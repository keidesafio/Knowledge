01 / MODEL LANDSCAPE

まず、各社のシリーズとサイズを知る

同じシリーズでも、小型モデルと大型モデルは更新時期が異なる。ここではローカルのテキスト業務に関係する代表7社の公開モデルを、サイズ帯ごとに整理した。各欄は確認できた現行世代・派生を示し、全メーカー・全用途の網羅的な発売順ランキングではない。

B＝10億パラメータ

4Bはおおむね40億規模。大きいほどメモリが必要になるが、数字だけで日本語や業務の得意・不得意は決まらない。

4bit量子化で軽くする

重みを少ないビット数で保持する方式。配布ファイルを小さくできる。QATは量子化を考慮した学習で、低ビット化による品質低下を抑える狙いがある。

MoEの「A」は稼働規模

35B-A3Bは総量35B、1トークンで稼働する部分が約3B。CPUの計算量が小さくても、保持する重みは3B分では済まない。

03 / WHY THESE TWO

今回のPCでは、この2モデルから試す

選定理由は、公開されていること、配布サイズが現実的なこと、CPU・16GBの個人検証があること。全モデルを同条件で比較した性能順位ではない。

日本語文書の比較軸

gemma4:e4b-it-qat

6.1GB ダウンロードサイズ

PR説明文の整形や、短い仕様から受入条件を抜き出す作業を最初の対象にする。日本語文書を扱った同条件の検証から考えた応用案。

Core i5-1145G7・16GB・CPU推論の個人記録では、筆者がE4B QATを使いやすいと評価。架空資料による単発の観察であり、一般的な優位性の証明にはしない。[11]

軽量なコード・短文処理の比較軸

qwen3.5:4b

3.4GB ダウンロードサイズ

関数単位のコード相談や、短い文章の要約を最初の対象にする。CPUだけで具体的な課題を実行した記録がある。

Ryzen 7 7735HS・16GBの個人記録では、Think OFFでPython関数生成やバグ修正を実施。回答の誤りも報告されており、テスト・原文照合を組み合わせる。[12]

結論：既存PCで2モデルを同じ業務に当て、修正時間まで比較する

関数の読解・テスト案・局所的な修正はQwenから、PR説明文・仕様の整理はGemmaから着手する。普段の開発から題材を選び、同じ課題で両方を比較する。次章で、各作業へ応用できると考える理由と成果物を示す。

Granite4.2 3Bなど、公開時期がより新しい小型モデルもある。「最も新しい2つ」という理由での推薦ではなく、今回の業務説明に使える実例のある2つを最初の試行対象とした。ほかの候補の性能が低いと結論づけるものではない。

04 / EVERYDAY ENGINEERING

日々の開発で、まず任せる6つの作業

コードを読む、テストを書く、エラーを調べる、変更内容を説明する。普段の開発作業を、16GB・CPU推論で試しやすい単位に分ける。特定の業界・帳票・閉域環境は前提にしない。まず日常の小さな作業で品質を確かめ、Copilotとの使い分けは次章で判断する。

いつ使うか任せる作業・受け取るもの最初の比較候補人の作業がどう変わるか
初めて触る関数を読むとき入力・出力・分岐・副作用をまとめた読解メモQwen3.5 4B最初の見取り図を得て、怪しい分岐をコードで確認する。
実装後にテストを足すとき境界値の表と、既存形式に沿った単体テスト案Qwen3.5 4B白紙からの列挙を減らし、期待値と漏れを確認する。
エラーが出て手が止まったとき原因候補・切り分け手順・小さな修正案Qwen3.5 4B調べる順序を整理して、一つずつ再現・検証する。
データ加工を手で繰り返しているときCSV・JSON等を加工する短い補助スクリプトQwen3.5 4B入力例から処理の下書きを作り、実データ投入前に試す。
PRを出す・変更を説明するとき変更理由・内容・確認結果・未確認を揃えた説明文Gemma4 E4B QAT箇条書きの開発メモを整え、事実の確認に集中する。

「できると考える理由」を、業務へ移せる形で読む

共通するのは、必要な情報を入力に入れる → 一つの変換・説明・提案をさせる → コード・テスト・原文で照合するという形。Qwenは小さなコード課題の実行記録、Gemmaは日本語文書の読解・整形の検証を根拠に、近い作業へ応用する。パラメータ数や量子化だけから業務の成功を説明しない。

確認できた個人実例

Chandanrohit氏はRyzen7 7735HS・16GB・CPU推論で、重複検出関数の生成、ループ中の変更バグの修正、短文要約を実施。前二者はThink OFFで1分19秒、1分38秒と報告。説明の誤りも掲載している。[12]

Gemma：日本語文書の読解・整形

なぜこのモデルで取り組めると考えるか

根拠：Qwen4Bで小さな関数の生成・修正を行った記録がある。[12] 応用の理由：ここで必要なのは、変数の流れや条件分岐を読み、自然言語へ変換する能力。判断に必要な範囲を関数と依存部分に絞れば、コード課題で使われた能力を応用できると考える。

依頼の仕方

別の業務への応用

確認：説明された分岐が実在するか、入力例の結果が合うかを確認する。コード読解の正確性を個人実例だけで保証はできない。

02 / テストを書く

仕様から境界値を並べ、単体テストの下書きを作る

そのまま日常で使う場面

関数を実装した直後、バグ修正で再発防止テストを追加するとき。対象関数・本来の仕様・既存テスト1件を渡す。実装だけを見せると、現在のバグを正しい仕様として追認する恐れがある。

入力例送料計算：購入額5,000円以上は無料、それ未満は500円。会員は金額を問わず無料。負の購入額はエラー。

受け取りたい成果物

なぜこのモデルで取り組めると考えるか

根拠：Qwen4Bには短いPython関数を生成した実行例がある。[12] 応用の理由：既存テストを見本にし、仕様の条件を具体的な入力へ置き換える作業は、小さなコード生成へ分解できる。条件整理とコード生成を分けると、間違いを途中で見つけやすい。

小型モデルで扱いやすくする条件

1関数・1仕様から始める。正解表は人が先に確認し、モックが必要な依存関数も入力に含める。多数のサービスをまたぐ結合テスト全体は別の評価対象にする。

別の業務への応用

入力チェック、権限条件、ページング、日付の範囲指定。共通する能力は、条件を具体的な確認ケースに展開してコード化すること。

確認：テストが実行できること、期待値が仕様と一致すること、修正前のバグで失敗することを確認。生成件数の多さやカバレッジだけで合格にしない。

03 / エラーを調べる

エラーと該当コードから、最初に確認する箇所を絞る

Qwen3.5 4B局所的なバグ修正の実例からの応用案
そのまま日常で使う場面

ローカル実行やテストで例外が出たとき。エラー全文、該当関数、再現入力、期待動作、言語・ライブラリのバージョンをまとめて渡す。

入力例TypeError: 'NoneType' object is not iterable
該当箇所：itemsをfor文で処理している。
呼び出し側の入力：{"items": null}
仕様：itemsがnullの場合は空の一覧として扱う。
受け取りたい成果物

候補：「itemsがNoneのまま反復処理へ入った」。確認箇所：呼び出し直前の値。修正案：Noneの場合だけ空配列に正規化。再発防止：null・空配列・通常配列のテスト案。

なぜこのモデルで取り組めると考えるか

根拠：Qwen4Bでループ中の変更バグを修正した記録がある。[12] 応用の理由：エラー文、コード、再現入力が揃うと、原因候補を局所的な言語の挙動に絞れる。システム全体の未知の原因を当てる必要が少なくなる。

依頼の仕方

原因候補は最大3つ、それぞれに「根拠」「確認方法」を付ける。修正は最小差分で求める。コードにない外部障害を断定したら、提案を採用せず追加調査する。

別の業務への応用

JSONキーの欠落、型の食い違い、パスの組立てミス、ループの取りこぼし。入力と期待結果を示せる不具合の一次切り分けに広げられる。

確認：同じ入力で再現させ、候補の修正後に症状が消えるかを見る。競合・性能・分散システムの障害などは、測定や広い文脈が必要で、この例から成功を推定できない。
04 / 小さな自動化を書く

繰り返すCSV・JSON加工を、短いスクリプトへ変える

Qwen3.5 4B関数生成の実例からの応用案
そのまま日常で使う場面

調査用のCSVから対象行を抜く、APIレスポンスを見やすくする、テストデータを整形するなど、手で同じ操作を繰り返すとき。

入力例列：id,status,updated_at
やりたいこと：statusがfailedの行だけを別CSVへ出力し、idの先頭ゼロと行順を保つ。入力ファイルは変更しない。Python標準ライブラリだけを使う。
受け取りたい成果物

CSVを読み、新しいCSVへ書く数十行程度のコード、実行方法、入力・期待出力の小さなサンプル。読込→変換→出力が見渡せるサイズで作らせる。

なぜこのモデルで取り組めると考えるか

根拠：Qwen4Bには重複検出関数の生成例がある。[12] 応用の理由：条件に一致する要素を選び、指定形式へ出す処理は、入力と出力を明確にしたコード生成に落とせる。標準ライブラリに限定すれば、未提示の社内APIや新しい依存関係を推測する余地も減る。

小型モデルで扱いやすくする条件

サンプル数行と期待結果を渡す。「便利なツールを作って」ではなく、「この列をこの条件で残す」と1処理に絞る。既存データの削除・上書きは行わない設計から始める。

別の業務への応用

JSONから必要キーだけ抽出、2ファイルのID差分、テスト用ダミーデータ生成。共通する能力は、自然言語で指定した変換を短いプログラムへ落とすこと。

確認：空データ、引用符・改行入りフィールド、文字コード、先頭ゼロをサンプルで確認する。SQLや正規表現だけで済む作業では、その案を作らせる使い方でもよい。

以上の作業はCopilotでも可能。ローカルで任せられる仕事の候補をまず具体化し、外部送信を避ける・オフラインでも使う・モデル版を自分で保持する必要があるときに、次章の利点が加わる。通常の開発作業だけでも試せるが、Copilotより高品質・高速になるとは前提にしない。

05 / THE REQUIREMENTS CLOUD CHAT CANNOT MEET

Copilotがある職場で、ローカルを追加する明確な理由

ここでのCopilotは、エンジニア向けのGitHub Copilot Chatをクラウドモデルへ接続して使う現状を想定する。導入の理由が最も明確なのは、「入力を外部へ一切送れない」または「外部ネットワークなしで推論したい」という要件がある場合。この要件はモデルの回答能力ではなく、実行場所で決まる。

必須要件と実際の仕事現在のクラウド接続Copilot Chatローカルで実現する構成今回の提案
外部送信ゼロ
社内コードをそのまま読解・テスト作成に使う		この要件を満たせない。クラウド推論には入力の送信が必要。学習利用の有無とは別の条件。ローカルファイル→ローカルモデル→ローカル保存。検索・外部ツールを使わず、送信経路を閉じる。単体テスト案をQwenで試す。社内固有の型やコードを外部へ渡さず、入力に含められる。
外部ネットワークなし
ネットに接続できない時間にもエラーを調査		クラウドモデルへ接続できず推論できない。モデルと実行環境を事前導入し、CPU推論。ローカルのエディターとテスト実行環境で完結。エラーの一次切り分けをQwenで試す。モデルを事前取得しておけば、ネット接続なしで候補を得られる。
モデルの重みを保管して同じ版を使い続ける
テスト案やPR説明文を生成する開発補助ツールの版を管理		サービス側の提供・更新・廃止に依存する。クラウドモデルの重みを利用者が保管して推論する運用はできない。取得した重み、モデルID、実行ソフト、設定を保管し、更新を管理する。出力の完全一致は別途評価。開発補助ツールへ組み込む段階で適用。タグ名だけでなく取得版を記録する。

ローカル推論の実行とクラウド機能の無効化はOllama公式FAQに説明がある。[17] 「ローカルモデルを選んだ」だけでアプリ全体の外部通信がなくなる保証にはならない。上記の運用では、クラウドへのフォールバック・外部検索・同期先を含めてローカルに揃える。

一方、バッチ化や料金の話は、こう判断する

フォルダー監視・定期処理

変更メモからPR本文の下書きを保存する仕組みは、クラウドAPIやCopilotの周辺機能を使って構築できる場合もある。自動化そのものをローカル固有の能力とはしない。

ローカルの利点は、その処理を外部送信なしで実装でき、推論を自作アプリから呼び出せること。上表の要件を持つ業務に組み込むと、追加する理由が明確になる。

既存Copilotとの費用比較

すでに使えるCopilotで仕事が完了するなら、ローカル導入だけで費用削減とは言えない。ローカルには電力・待ち時間・導入保守の負担がある。

追加理由は「クラウドへ渡せなかった業務にも使えること」から評価する。利用量が増えた場合は、実際の契約費と人の作業時間を含めて比較する。

Copilotのチャット画面にローカルモデルを追加してもよい

VS CodeはOllamaなどのBYOKモデルとオフラインチャットをサポートしている。したがって「Copilotという画面では絶対に不可能」とは言えない。上表の要件を満たすには、現状のクラウド推論をローカル推論へ切り替える構成を追加する。チャット用途は既存UI、定期処理は自作スクリプト、と使い分けられる。[14]

BYOKだけではインライン補完や埋め込み依存の検索は置き換わらない。会社のモデル接続ポリシーと、使用する拡張機能・補助モデルの経路を合わせて確認する。

導入判断：日常の開発作業で試し、運用上の利点と合わせて選ぶ

まずQwenで関数のテスト案、GemmaでPR説明文を作る。ローカルの品質・待ち時間が許容でき、外部送信回避やオフライン利用にも価値があれば継続する。そうした要件がなく、Copilotで十分に効率よくできる作業では、引き続きCopilotを使う判断も合理的。

06 / FIRST TRIAL

次の開発作業を題材に、確認・修正まで含めて比べる

01 / テスト

今の関数を1つ

仕様と既存テストを渡し、Qwenでテスト表を作る。期待値の誤り、見落としていた境界値、テストを使える状態に直す時間を記録する。

02 / 説明文

次のPRを1件

変更メモをGemmaで整える。未実施のテスト成功などが追加されていないかを確認し、手書きと完成までの時間を比べる。

03 / 調査

直した不具合を1件

答えの分かる過去のエラーをQwenへ渡す。原因候補にたどり着くか、提案した確認手順が実行可能かを確かめる。

最初の1件で使い方を調整し、その後は同じ種類の作業5件程度で比較する。評価件数は試行計画の提案。自分で考える時間、モデルへの入力準備、待ち時間、確認・修正の時間を分けて記録する。

PC側の初期条件

  • 現行Ollamaを使用。初回はDocker等を追加せず、モデルを1つずつ実行。
  • 2モデルの配布合計は約9.5GB。ダウンロード・更新の余裕を含め、空きSSD 20GB程度を確保する計画にする。
  • Think OFF、短い入力、コンテキスト4Kから開始。これは本資料の試行設定で、公式最低要件ではない。
  • RAM不足やスワップが出る場合は入力を短くし、常駐アプリを減らす。入力が枠を超える場合は分割する。

記録するもの

  • CPU型番、RAM、Ollamaのバージョン、モデルタグとID。
  • 入力長、コンテキスト設定、Think設定。
  • 読み込みを含む時間と、読み込み済みの完了時間。
  • 最大RAM使用量、誤りの数、最終成果物までの人の修正時間。
  • Copilotと比較できるデータでは、同じ課題で比較する。
Ollamaで試す最小コマンドを表示
# PowerShell：モデルの取得（初回はネット接続が必要）

ollama pull gemma4:e4b-it-qat

# 起動後のチャット内で入力

導入の判断は「生成できた」から一歩進める

人の確認・修正を含む所要時間が短くなる仕事、または外部送信できないため従来AIを使えなかった仕事を採用対象にする。16GBのまま価値を確認し、品質不足なら別モデル、速度不足ならハードウェアを次に比較する。
